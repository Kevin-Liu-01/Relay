  • The harness accepts only supported actions, so a model response cannot execute arbitrary code.
  • After each action, it reads the updated page before asking the model what to do next.
  • The run stops when the model finishes or reaches an action, time, or spending limit.

I grade saved data, not visible text or a completion message

  • The grader is code that checks the stored messages, topics, and other workspace data.
  • For the editing task, the original message must contain the requested text and all unrelated data must stay unchanged.

I tested correct and nearly correct outcomes separately

Can the UI do it?Run a scripted solution Search → edit → Save → inspect the stored messageThe requested change must persist.
Can the grader catch a near miss?Alter a known correct result Wrong destination, wrong author, or one extra changeThe altered result must fail.
Can I explain a model's result?Reopen the recorded run Read its actions and check its saved data againThe recorded grade must agree.
  • These checks separate application bugs, grading bugs, and agent mistakes without paying for more model calls.
  • A scripted solution still knows my intended answer, so it cannot prove that a new reader understands the task.
  • Software verification · The longer-workflow grader tests cover 84 valid and 2,583 invalid states across seven seeds.

Two agents must not share mutable workspace data

  • If agent A edits a message, agent B must still see its own unchanged copy.
  • I give each run a separate SQLite file and a fresh browser context, which is an independent browser session.

Small databases do not mean cheap browser runs

Workspace dataOne SQLite file per runSimple creation, reset, and deletionMeasured: 48 KiB per fixture after one post
Browser executionFresh browser per experiment runNo browser state carried into the next runCost: startup time and browser memory
EvidenceRecord actions and workspace statesReview failures without new model callsCost: growing files and disk writes
  • I share application code, but keep each run's data separate.
  • The storage test did not measure full browser memory, so it cannot tell us how many agents fit on a machine.
  • The experiment runner creates and closes an environment per run. Reusing a browser across fresh contexts is a future optimization.
  • API execution can omit the browser when visual recording is disabled. The reported interface study kept observer recording enabled.

I would scale with a fixed number of run workers

  • The sequential collections do not demonstrate multi-agent throughput.
  • A queue would admit work only when a worker has capacity, instead of launching a browser for every incoming request.

More workers can finish more runs at once. They do not make an individual model request faster.
  • Test 1, 4, 8, and 16 workers: successful runs/hour, full process-tree memory, provider limits, and cleanup after a killed worker.
  • Use separate processes or containers for stronger containment. Browser pooling trades lower startup cost for shared failure risk.
