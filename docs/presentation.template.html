  • A browser edit requires finding the editor, entering text, and saving the change.
  • The actor API can request that edit directly, so the workspace changes without a browser click.
  • The same grader checks the result, but the model uses different information and actions to reach it.
  • Page JSON describes page controls, not the underlying database. Actor API access exposes broader structured data.
  • The harness uses a shared JSON action protocol, not each provider's native computer-use protocol.

  • A failed run can come from the app, the grader, or the model, so I check each separately.
  • I inspect the saved actions and data to explain the failure without buying another attempt.
  • A scripted solution tests my intended answer, not whether another reader understands the task.
  • Software verification · The longer-workflow grader tests cover 84 valid and 2,583 invalid states across seven seeds.

Each model starts with its own copy of the task

  • If a previous run leaves the message at 15:00, the next model starts with work already done.
  • Each run gets its own SQLite database and browser session, so its actions change only its own workspace.

Browsers and recordings have separate resource costs

{{ICON_DATABASE}}Workspace dataOne SQLite file per runThe next model does not inherit earlier editsMeasured: 48 KiB per fixture after one post
{{ICON_BROWSER}}Browser executionFresh browser per experiment runNo browser state carried into the next runCost: startup time and browser memory
{{ICON_EVIDENCE}}EvidenceRecord actions and workspace statesReview failures without new model callsCost: growing files and disk writes
  • Stored actions and states let the replay show each run without calling the model again.
  • The 306-run collection paused when free disk space fell below its storage safeguard.
  • The storage test did not measure full browser memory. Current runs create and close their own environment; browser reuse is untested.
  • API execution can omit the browser when visual recording is disabled. The reported interface study kept observer recording enabled.
  • Recorded storage stop · Existing evidence was preserved.

A queue would limit how many browsers run at once

  • Starting a browser for every visitor could exhaust memory and slow or interrupt active runs.
  • I would queue new runs until a worker is free, while keeping each active run's data separate.

A visitor would wait for a free worker before their run starts. More workers could reduce the queue, not model response time.
  • The collections ran sequentially, so capacity is unproven. Test 1, 4, 8, and 16 workers for throughput, memory, provider limits, and crash cleanup.
  • Use separate processes or containers for stronger containment. Browser pooling trades lower startup cost for shared failure risk.
